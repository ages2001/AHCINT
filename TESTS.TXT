AHCINT - test results for this release (QEMU 8.2, ich9-ahci)

bin\NT\ahcint.sys was built from these sources with i686 MinGW (GCC 13)
against import libraries generated from NT 3.1's own SCSIPORT.SYS and
NTOSKRNL.EXE exports; it imports nothing NT 3.1 lacks. src\NT\build.bat
(MSVC 4.0 + NT4 DDK) builds the same sources. For the Windows 95 tests
bin\9X\AHCINT9X.MPD was built from the same sources with MinGW as well
(PE layout as from MSVC: file and section alignment 200h);
src\9X\build.bat builds the same sources with MSVC.
bin\2KXP\i386 and bin\2KXP\amd64\ahcint.sys were built with MinGW
(i686 / x86_64) against import libraries generated from Windows 2000's
and XP x64's own SCSIPORT.SYS and NTOSKRNL.EXE; src\2KXP (DDK build)
builds the same sources.

QEMU used for the 1.5 tests
- QEMU 8.2.2, patched (test environment only):
  - ATA disks with 1024/2048/4096-byte logical sectors (IDENTIFY words
    106/117-118), also for NCQ commands.
  - Port multiplier emulation (AHCI_PM=<port>): CAP.SPM, a multiplier
    with two device ports (GSCR product 37261095h, PSCR SStatus/SError/
    SControl, READ/WRITE PORT MULTIPLIER), PM port n = IDE unit n of
    that AHCI port, software reset per PM port with the device's
    signature, the PM signature on port 15. On the other ports the PM
    port field is ignored, as by a directly attached device.
  - Fix: an NCQ command accepted after a failed command carried the old
    error status in its D2H FIS (QEMU raised TFES for a good command).
- I/O errors injected with QEMU's blkdebug driver (EIO on every read
  of one sector).

New in 1.5 - what was tested

TRIM, VPD, LOG SENSE, shutdown standby, version resource
- Windows 2000 SP4, data disk on ich9-ahci port 1 with QEMU
  discard=unmap, discard_granularity=512, rotation_rate=1 (an SSD for
  IDENTIFY: word 169 TRIM, word 217 = 1). Feature test (featst, SCSI
  pass-through and miniport IOCTLs): READ CAPACITY(16) LBPME 1, VPD
  00h lists 80h B0h B1h B2h, B0h (max unmap 3FFFC0h, 64 descriptors),
  B1h rotation 1, B2h LBPU, LOG SENSE 00h (00 0D 2F), 0Dh (temperature
  31 C from SMART), 2Fh, UNMAP of 16 blocks (they read back as zeros
  on the host image), UNMAP beyond the end (ILLEGAL REQUEST 21h), TRIM
  mode (an ordinary write is written, a pattern write becomes a TRIM,
  after TRIM_MODE_OFF the pattern is written): RESULT OK fails=0. The
  system disk (no discard on the image) answers the same, except that
  its blocks keep their data after UNMAP (QEMU ignores the TRIM).
- System shutdown: "Port 0.0: standby for shutdown" (SRB_FUNCTION_SHUTDOWN
  reaches the driver since it declares CachesData).
- File properties of every binary show version 1.5.0.0
  (OriginalFilename ahcint.sys / ahcint9x.mpd).
- trimnt on a 256 MB FAT volume on the AHCI disk (discard=unmap, the
  image with 55 MB of stale blocks): "Scsi2: AHCINT TRIM mode on", the
  free space trimmed, files deleted; the image went from 63.7 MB to
  10.6 MB allocated, sumtool FILES 5 ERRORS 0, CHKDSK clean.
- Release build (bin\ as shipped) on Windows 2000 next to IDENT, MMCSDNT
  and NVMENT data disks: featst RESULT OK fails=0, trimnt, sumtool and
  CHKDSK on the volume OK. Windows 95: AHCINT9X installed for the AHCI
  function (New Hardware Found, driver from disk), sumtool FILES 5
  ERRORS 0 and w95io RESULT OK on the AHCI volume.

NCQ
- Windows 2000 (system disk and four data disks with 512, 1024, 2048
  and 4096-byte sectors on one controller, PnP interrupt): NCQ active
  on every disk, several commands queued per port. Per volume (NTFS):
  100 MB load test, copy of WINNT\INF and SYSTEM32\DRIVERS (1280
  files) compared by CRC32, re-read after a cold boot, chkdsk /f clean.
  The same with NCQ=0 (Fast Polling) for comparison.
- Windows NT 4.0 SP6, system disk on AHCI, UP (IRQ 11) and MPS HAL with
  2 CPUs (IOAPIC, IRQ 16): NCQ active, data disks with 512, 1024, 2048
  and 4096-byte sectors: CRC32 of the files on every volume, 100 MB load
  test per volume, chkdsk - no errors. Debug and release builds.
- Windows NT 3.1, system disk on AHCI: Fast Polling by default (as
  before). With NCQ=1 (INTx connected level-sensitive on the EISA bus):
  NCQ active, up to 16 commands queued, load tests on 1 KB and 4 KB
  NTFS volumes and CRC32 comparison - no errors.
- Windows XP x64, text-mode setup with F6 (bin\2KXP\amd64): NCQ active
  already in text-mode setup (IRQ 10); partition, format, file copy,
  first boot from the AHCI disk into GUI-mode setup.
- Error recovery (Windows 2000, disk with one unreadable sector):
  overlapped and single reads around it, three rounds; only the read of
  the bad sector fails (I/O device error), every other read succeeds,
  NCQ stays on. Same result with NCQ=0. This run found the stale
  PxTFD.ERR problem fixed in 1.5 (see the changelog): before, the next
  Fast Polling command after a failed one could fail as well.
- Not reproduced here: the missing-interrupt fallback to Fast Polling
  (QEMU always delivers the interrupt), and the NCQ error log (QEMU does
  not implement READ LOG EXT; the single-command path was used).

Port multipliers (emulated, see above)
- Windows 2000: two disks behind a multiplier on port 5 (512 and 4096-
  byte sectors) seen as LUN 0 and LUN 1 of target 5. A tagged 64 KB
  pattern written to each through \\.\PhysicalDriveN, read back and
  compared, then found on the host in the right image file only; the
  feature test below on both disks.
- Windows 95: two disks behind a multiplier (512 and 1024-byte sectors,
  FAT16) as D: and E:; pattern test on both (96 MB / 32 MB), XCOPY with
  CRC32 compare on D:, images checked on the host - no errors.
- The other ports, with CAP.SPM set, still find their directly
  attached disks.

Power management
- Windows 2000 (UP ACPI HAL, QEMU PIIX4 S3/S4 enabled): hibernation
  (S4) through SetSuspendState with NCQ active. The driver is stopped
  through HwAdapterControl, the dump stack loads a second instance
  (Fast Polling, 4.4 KB device extension) which writes the hibernation
  file, and on resume ScsiRestartAdapter sets the HBA up again. After
  resume the four data volumes' CRC32 lists are unchanged, chkdsk is
  clean and a load test passes. The first try failed: the dump stack
  could not allocate the 38 KB device extension of the test build
  (C000009Ah); 1.5 keeps it at 4.4 KB.
- S3 (standby): Windows 2000 under QEMU/SeaBIOS did not come back from
  S3 in this setup - also with the system disk on QEMU's IDE controller
  and with NCQ=0, so the problem is the environment. The driver's
  part (stop, restart, re-initialization) was logged as expected.
  Worth a check on real hardware.
- AHCINT power IOCTL on NT 3.1, NT 4.0 and Windows 2000: POWER_DOWN
  (flush, standby, ports stopped), the next request brings the HBA
  back; POWER_DOWN, POWER_UP, read - no errors. Also with the
  multiplier on Windows 2000 (the PM is enumerated again).

Link speed
- QEMU patched to leave a Gen1 limit (PxSCTL = 310h) after every port
  reset, as some firmware does. NT 4.0, system disk and four data disks:
  every port is renegotiated once at initialization (COMRESET with
  PxSCTL.SPD = 0), the system boots from AHCI, load test on four volumes,
  CRC32 lists and the feature test - no errors.

F6 disks, GUI-mode setup
- Windows XP x64, text-mode setup with F6 (bin\2KXP\floppy_amd64), AHCI
  disk and setup CD on AHCI: text-mode setup, first boot from AHCI,
  GUI-mode setup through device installation up to Regional Options
  without a "Files Needed" prompt. Before, GUI-mode setup asked for
  OemDir\amd64\ahcint.sys (text-mode setup copies the F6 files flat,
  the INF pointed to the amd64 subdirectory); the F6 disks now carry a
  flat INF. Found and checked the same way with nvme2k.

Final binaries (rebuilt with the link speed change)
- NT 4.0 UP: load test on four volumes, CRC32 lists, feature test on
  four disks, chkdsk. Windows 2000: feature test on four disks, CRC32
  lists. Windows 95: 512-byte data disk, pattern test, XCOPY with CRC32
  compare, image checked on the host. No errors.

Controllers without devices
- Checked after a report of a hang at "Starting up" with a controller
  that has no disk (seen with nvme2k, an NVMe controller without
  namespaces; fixed there). AHCINT: an HBA with no device on any port,
  a second empty HBA next to the system HBA, and a port with a device
  that does not answer IDENTIFY DEVICE. Before, the last case was
  presented as a disk with no capacity; it is now reported as no
  device. Boot and disk enumeration checked on NT 3.1, NT 4.0 (UP),
  Windows 2000 (empty AHCI HBA plus an empty NVMe controller next to
  the system disk, boot to the desktop in 55 s) and Windows 95 (second
  empty HBA, desktop) - no hang, no phantom drives.

OEMSETUP.INF (NT 3.1 - 4.0)
- Now also sets Start = 0 for the disk class driver (scsidisk on NT 3.x,
  disk on NT 4.0). Tested with the same INF code in the nvme2k package:
  NT 4.0 (Control Panel - SCSI Adapters - Have Disk) and NT 3.1 (Windows
  NT Setup - Add/Remove SCSI Adapters - Other), each with a class driver
  key set to Start = 3 beforehand: afterwards Start = 0, the miniport
  installed as a boot driver and working after the reboot.

Feature test (a small tool, on every data disk of Windows 2000, NT 4.0
and NT 3.1, and on both disks behind the port multiplier)
- AHCINT GET_INFO; SMART through "SCSIDISK": VERSION, IDENTIFY, ENABLE,
  READ ATTRIBUTES, RETURN STATUS (4Fh/C2h).
- SCSI pass-through: READ CAPACITY, ATA PASS-THROUGH(12) IDENTIFY DEVICE
  (PIO in), ATA PASS-THROUGH(16) SMART RETURN STATUS with CK_COND
  (descriptor sense 72h, ATA status return descriptor 09h), REPORT LUNS,
  MODE SENSE(10) caching page, MODE SELECT(10) write cache off -> MODE
  SENSE shows it off -> on again, SYNCHRONIZE CACHE, VERIFY(10) of 2048
  blocks, VERIFY(16), START STOP UNIT stop -> READ -> start.

Results of 1.4 (unchanged parts of the driver)

Test load used throughout: a CrystalDiskMark-like tool (no buffering,
write-through, overlapped I/O): 1 MB sequential write/read, 512 KB and
4 KB random write/read, 4 KB at queue depth 32, then a full re-read.
Every sector carries its own number and a generation tag, so a misplaced,
stale or lost write is detected.

Windows NT 3.1 SP0, Standard HAL
- Driver load with NT 3.1's ScsiPort (40h-byte HW_INITIALIZATION_DATA,
  ISA bus, PCI found through ports CF8h/CFCh).
- AHCI data disks: FAT and NTFS formatted by NT 3.1, copies compared,
  chkdsk clean; files also checked from the host image.
- ATAPI CD-ROM on AHCI (CDFS), CRC32 of every file.
- Boot from AHCI, boot.ini multi(): 32 MB up to 3 GB RAM with the
  Windows 2000 NTLDR/NTDETECT.COM, 32/256 MB with NT 3.1's own NTLDR.
- Boot from AHCI, boot.ini scsi() with NTBOOTDD.SYS: both loaders.
- LBA48: NTFS partition past sector 2^28 on a 140 GB disk.
- Two AHCI controllers (32 MB to 1 GB RAM).
- Load test at 2 GB: D: (FAT) 200 MB, F: (NTFS, LBA48) 300 MB,
  C: 60 MB - no errors.

Windows NT 3.51 SP5, Standard HAL (system disk on AHCI)
- FAT/NTFS format, copies, CD, load test D: 300 MB, E: 4500 MB
  (file larger than 4 GB), C: 100 MB - no errors.

Windows NT 4.0 SP6, Standard HAL and MPS HAL (halmps.dll/ntkrnlmp.exe)
- UP: system disk on IDE and on AHCI, load test on FAT, NTFS and C:,
  two 1000 MB runs in parallel, one 4500 MB run - no errors.
- MPS, 2 and 4 CPUs, 256 MB to 2 GB: boot + concurrent load (three
  load tests, CD reader, xcopy) repeated 15 times - no bugcheck.
- Slow disk (QEMU throttled to 20 KB/s, one 128 KB write ~6 s): the
  previous build timed out after 3 s, stopped the port mid-transfer and
  QEMU crashed; this build completes the copy and fc /b finds no
  differences.

Logical sector sizes (QEMU 8.2.2 patched so that its ATA disks report
1024/2048/4096-byte logical sectors in IDENTIFY words 106/117-118)
- Windows NT 4.0 SP6: FAT and NTFS at 1024, 2048 and 4096 bytes, each
  formatted by NT 4.0; load test, copies compared by CRC32, chkdsk
  clean, files re-read after a cold boot. 512-byte disks re-tested.
- Windows NT 3.1 SP0: FAT at 1024 bytes; NTFS at 1024, 2048 and 4096
  bytes; load test and CRC32 comparison of copies. FAT at 2048/4096
  bytes formats and the volume is valid (fsck.fat on the host), but NT
  3.1's FASTFAT does not mount it. NT 3.1's FORMAT.COM faults
  (UNTFS.DLL) at the end of a 4096-byte NTFS format; the volume is
  complete and usable.
- Windows 95 (4.00.950), data disk on AHCI, FAT16 made on the host with
  the matching sector size: 512, 1024 and 2048 bytes work. Per size: a
  96 MB pattern file (sequential, random 4 KB and 32 KB writes, full
  verify), XCOPY of WINDOWS\SYSTEM (274 files) compared by CRC32 in the
  guest, then the image checked on the host (fsck.fat, pattern file,
  every copied file) - no errors. Windows 95 reports the sector size
  through GetDiskFreeSpace (1024/2048).
  4096 bytes: the driver reads the MBR and boot sector at boot (4096
  bytes each), after that Windows 95 sends only TEST UNIT READY and
  answers every access with "General failure reading drive D".
- Not covered: Windows 98/Me, 2000/XP, NT 3.50/3.51 with large sectors.

Windows 2000 (5.0.2195, system disk on AHCI, booted with bin\2KXP\i386)
- Data disks with 512, 1024, 2048 and 4096-byte logical sectors on one
  controller. Each volume formatted by Windows 2000 as FAT, then as
  NTFS. Per volume: 100 MB load test, copy of WINNT\INF and
  SYSTEM32\DRIVERS (1281 files) compared by CRC32, then after a cold
  boot all files re-read and compared, chkdsk /f clean. FAT volumes
  also checked on the host with fsck.fat - no errors.

Windows XP x64 (5.2.3790), text-mode setup with F6 (bin\2KXP\amd64)
- Reproduced with the previous build: AHCI controller with the target
  disk and the setup CD, driver from the F6 floppy -> STOP 0x7B
  (C0000034). The driver loaded, ScsiPort's AddDevice succeeded,
  IRP_MN_START_DEVICE failed (STATUS_UNSUCCESSFUL) before HwFindAdapter
  was called. Cause: Parameters\PnpInterface missing from the text-mode
  registry (see README, Windows 2000/XP/x64 specifics); adding it to
  txtsetup.oem's [Config] section does not help, since setup applies
  those values only to the installed system.
- The F6 disks' txtsetup.oem now also list PnpInterface in [Config]
  (for the installed system); the driver no longer depends on it.
- This build: setup finds the disk and the CD, partition/format (NTFS)
  and file copy complete, the first boot from the AHCI disk reaches
  GUI-mode setup (driver loaded from the installed system). The rest of
  GUI-mode setup was not run (product key).

Windows 95 test environment notes
- The system disk was on QEMU's IDE controller, the AHCI controller
  presented as ICH8M (8086:2829) like in the VirtualBox VM. With the
  system disk on AHCI, SeaBIOS's INT 13h made Windows 95 stop with
  "While initializing device IOS: An I/O subsystem driver failed to
  load" - also with the AHCI driver removed, so not driver related.
- When SeaBIOS also serves an AHCI disk through INT 13h, Windows 95
  shows it twice: once through AHCINT9X and once in MS-DOS
  compatibility mode (same with the VM's own ahcint9x.mpd). The tests hid
  the AHCI disks from SeaBIOS (prog-if 00); the driver accepts the
  ICH8M by its ID.

Not reproduced here
- CrystalDiskMark itself: the supplied CrystalMark Retro 2.1.0 package
  holds only the XP SP2+ executables (they import GetFileSizeEx,
  SetFilePointerEx, EncodePointer, ... which NT4 lacks), not
  CrystalMarkRetroNT.exe. The fix above addresses the one failure mode
  found under a CrystalDiskMark-like load.
- The intermittent 0xA on MPS HALs did not occur in any run, with or
  without the timeout change. The timeout change removes one MP-only
  race (see README, Command timeout); whether it is the reported one
  could not be confirmed.

Test environment note
- In this QEMU setup, scsi() boots of NT 3.1 sometimes stopped in NTLDR
  with "could not read from the selected boot disk" while the emulator
  received no outside events. It happened identically with the previous
  release, with NT 3.1's own NTLDR and with HwResetBus disabled, never
  with multi(), and never while the QEMU monitor was active. It was not
  seen on the previous day's host and is treated as an emulator timing
  artifact; worth one check on VirtualBox or real hardware.
