AHCINT - test results for this release (QEMU 8.2, ich9-ahci)

Hibernation on Windows 2000 and XP x64 (2026-11-03)

- Display: S4 needs a driver on the display adapter. Windows 2000 with
  -vga cirrus: the in-box Cirrus Logic 5446 driver (display.inf),
  installed through SetupAPI. XP x64 with the std VGA: the in-box
  "Standard VGA Graphics Adapter" (display.inf, vgapnp.sys, which XP x64
  had not picked for the device), installed the same way. No driver was
  downloaded: the one free QEMU display driver source found
  (roytam1/vbemp, VBE miniport for NT 3.x) is x86 only and has no power
  management, so it would not have let S4 through either.
- Windows 2000 (256 MB, ACPI HAL, patched QEMU with AHCI link power
  management, NVMe HMB 8 MB and APST): system disk on AHCINT (ICH9
  port 0), 256 MB disks on AHCI port 1 (AHCINT), on the PIIX3 primary
  and secondary master (IDENT; the CD as secondary slave), an NVMe
  namespace (NVMENT) and an SD card on sdhci-pci (MMCSDNT). Power
  capabilities S3 1 S4 1, hibernation file reserved. bench.exe on the
  five data disks, hibernate, resume, bench again, hibernate, resume,
  bench again: all without errors; DRIVER.CAB from the CD and FC: equal
  afterwards; IDENTIFY through \\.\PhysicalDriveN still reached each
  disk (the SD card has none). After the second resume QEMU's log shows
  APST on, the HMB given again (2048 pages, every descriptor checked)
  and ALPE set on the AHCI ports; before the final power-off ALPE and
  ADSE were cleared (full power).
- XP x64 (512 MB, stock QEMU): system disk on IDENT (PIIX3 primary
  master), data disks on the primary slave and secondary master
  (IDENT), AHCI port 1 (AHCINT) and NVMe (NVMENT), the CD as secondary
  slave. S4 1, hibernation file reserved; the same two cycles with
  bench.exe before and after each: all without errors, then DRIVER.CAB
  and FC equal, IDENTIFY through each \\.\PhysicalDriveN.
- After a resume both systems lock the session; a power-off asked for by
  a program in that locked session (ExitWindowsEx returned success) did
  not power the machine off, it stayed at the logon screen. With the
  password on resume turned off (powercfg /globalpowerflag off /option
  resumepassword, XP x64) the same program powered off at once after a
  resume. Windows behaviour, not the drivers'.

SMART through the disk on XP x64 (added to 1.7.0.0, 2026-11-03)

- SMART through \\.\PhysicalDriveN (disk.sys) on XP x64: the request
  goes to the disk's PDO as IOCTL_SCSI_MINIPORT, which XP x64's ScsiPort
  (5.2.3790.1830) answers on a PDO with STATUS_INVALID_DEVICE_REQUEST
  (disassembly of its PDO device-control routine; only the adapter's
  device object takes it): smartt.exe reported ERROR_INVALID_FUNCTION on
  every disk of the driver, \\.\ScsiN: answered. The stock atapi.sys
  (not a ScsiPort miniport) answers on the same image. With the
  IRP_MJ_DEVICE_CONTROL front end the request is passed through the PDO
  as SRB_FUNCTION_IO_CONTROL (ScsiPort's PDO routine takes that function
  and fills in the disk's address).
- A first build without an MDL in that request stopped XP x64 with
  STOP D1 in ScsiPort (it maps the data of every request with
  DATA_IN/DATA_OUT through the IRP's MDL); with the MDL as below.
- XP x64 SP1 (5.2.3790.1830, ACPI HAL), an installed image moved to
  QEMU's PIIX3: system disk on the IDE primary master (IDENT), 256 MB
  disks as primary slave and secondary master, the XP x64 CD as
  secondary slave, a 256 MB disk on ICH9 AHCI port 1 (AHCINT), a 256 MB
  NVMe namespace (NVMENT); the three drivers installed with their INFs
  through SetupAPI. Release builds: bench.exe on the four data disks,
  DRIVER.CAB from the CD and FC: equal; IDENTIFY through
  SMART_RCV_DRIVE_DATA on \\.\PhysicalDrive0-4 returned each disk's own
  serial number (QM00001, PRISLAVE, SECMASTER, AHCIP1, NVME1), SMART READ
  DATA answered on each; 32-bit and 64-bit test programs; shutdown
  powered off.
- Windows 2000 (regression, release builds): IDENTIFY through
  \\.\PhysicalDriveN returned the serial of each disk of the driver
  (the 2000 ScsiPort passed these on before as well); bench, DRIVER.CAB
  and FC, SMART, hot plug and card change as before.

Link power management and DevSleep by default (added to 1.7.0.0,
2026-11-02)

QEMU's AHCI has neither; it was patched for these runs
(QEMU_AHCI_LPM=1): CAP reports SALP, PSC and SSC, CAP2 SDS and SADM,
PxDEVSLP keeps what is written (DSP set), IDENTIFY reports HIPM (word 76
bit 9), DIPM and DevSleep (word 78 bits 3 and 8), SET FEATURES
enable/disable SATA feature is accepted, and every change of ALPE, ASP,
ICC and ADSE is logged with the state of the port's engine. QEMU does
not change the link state itself (PxSSTS.IPM stays active).
- Windows 2000, debug build, no DriverParameters: ports 0 and 1 "link
  power management (Partial, device too)" and "DevSleep after 1 s
  idle"; QEMU: SATA features 03h and 09h on for both disks, ALPE 1 ASP 0
  for both ports, ADSE 1 written with the engine stopped (DITO 1000).
  bench, DRIVER.CAB from the CD and FC: equal.
- At shutdown (SRB_FUNCTION_SHUTDOWN for the system disk): "Port 0: link
  at full power" before the flush; QEMU: ADSE 0 with the engine
  stopped, ALPE 0, then ICC 1 (Active). Windows 2000 powered off.
- Hot plug with link power management on: port 1 pulled during the test
  program and plugged in again: "device removed", "device arrived",
  link power management set up again for the new device, test program
  afterwards without error.
- Release builds of this round: on the patched QEMU the same changes in
  its log, bench, DRIVER.CAB and FC equal; on the unpatched QEMU Windows
  2000 bench, FC and SMART, the hot-plug run, NT 4.0 (also SMART), NT
  3.51 and NT 3.1 copy and FC, and Windows 95 (AHCINT9X: both compares,
  the disk pulled and plugged in between): all as before.
- The QEMU without the patch (no SALP, no SDS): nothing is changed, as
  before (all other runs in this file).
- Not tested on real hardware: the link states themselves, the wake-up
  latency, and hot-plug detection while a link is in Partial or Slumber
  (the check reads PxSSTS.DET, which stays 3 in those states, and treats
  IPM 8 as linked).

Interrupt completion, Windows 95 Init Failure, 512 KB transfers, link
power, SMART, dump instance (added to 1.7.0.0, 2026-11-02)

Every command now completes by interrupt where the system has one:
queued (NCQ) and non-queued reads and writes (NCQ=0, or a disk without
NCQ), ATAPI, FLUSH, VERIFY and pass-through. Fast Polling (a short spin,
then 1 us steps) remains for systems without an interrupt, IRQ=0, the
crash dump / hibernation instance and the short commands at start-up.
- Windows 2000, system disk on port 0, 256 MB disk on port 1, SATA CD on
  port 2, debug build: bench.exe (sequential and random reads and
  writes, queue depths 1 to 32, verify passes): no errors; DRIVER.CAB of
  the XP x64 CD (62.7 MB) copied twice from the CD, FC: equal.
- The same with a build that turns NCQ off (every read and write a
  non-queued command completed by interrupt): no errors, FC equal.
- Windows 2000, port 1 pulled during the test program's writes and
  plugged in again (as in "Hot plug" below) with the interrupt path: the
  requests failed, the disk came back, test program afterwards without
  error.

  tables; MAXXFER=128 keeps 128 KB), Windows 2000: bench without errors,
  FC equal; 1 MB sequential reads at queue depth 4 more than twice as
  fast as with 128 KB requests in this QEMU. Disks without LBA48 get
  requests over 256 sectors split into 28-bit commands (not reached
  here: QEMU's disks have LBA48).

Hot plug (added to 1.7.0.0, 2026-11-02; on by default on NT, HOTPLUG=0)

QEMU 8.2.2 patched for these runs: while a file named after a drive's
serial number exists, that drive reads as pulled (AHCI: PxSSTS DET 0,
PxTFD 7Fh, PxSIG all ones, commands not started; IDE: every register
reads 7Fh, commands ignored); removing the file plugs it in again. The
test program writes, reads and verifies the raw disk (queue depths 1 to
32).
- Windows 2000, system disk on AHCI port 0, 256 MB data disk on port 1,
  release build, no DriverParameters:
  - pulled during the test program's writes: the requests failed, the
    program ended with errors (expected), the disk left the system;
    plugged in again: back, full test program run without error.
  - pulled while idle (debug build): gone within 2 s, back after the
    plug-in, test program without error.
  - link down for 0.9 s while idle (debug build): "link reset, same
    device(s)", the disk stayed in the system throughout, test program
    afterwards without error.
  - In an earlier run the disk did not come back after the plug-in: the
    test program still held the old disk open at that moment (it waited
    for a request that had failed at once, a bug of the program, fixed).
- Windows 2000 with DriverParameters HOTPLUG=0: the disk stayed listed
  while pulled (nothing checked), test program after the plug-in
  without error.
- Windows NT 3.1 (stock kernel, booted from AHCI port 0; Fast Polling,
  the timer is the only one the driver uses there), NT 3.51 SP5 and NT
  4.0 SP1, debug build of this version with no DriverParameters: port 1
  pulled and plugged in again ("device removed", "device arrived");
  logged on, ntoskrnl.exe copied to D: (FAT) and compared with FC:
  equal; the file read from the disk image on the host: equal.
  The stock NT 3.1 and 3.51 kernels needed QEMU's -icount (a slowed
  virtual CPU) to get past the boot screen in this emulator, with the
  in-box drivers too. The registry was changed offline only in place
  (a Start value), the driver put in place of an unused service.
- Windows 95: not run in this hot-plug round (AHCINT9X then ended in
  "Init Failure" before HwFindAdapter; the cause and the Windows 95 runs
  are under "Interrupt completion" above); hot plug stays off on 9x
  unless HOTPLUG=1.
- The NCQ watchdog and the hot-plug check share one timer; a request
  while one is pending is not passed on. All runs above used that.

New in 1.5 - what was tested

TRIM, VPD, LOG SENSE, shutdown standby, version resource
- Windows 2000 SP4, data disk on ich9-ahci port 1 with QEMU
  discard=unmap, discard_granularity=512, rotation_rate=1 (an SSD for
  IDENTIFY: word 169 TRIM, word 217 = 1). Feature test (featst, SCSI
  pass-through and miniport IOCTLs): READ CAPACITY(16) LBPME 1, VPD
  00h lists 80h B0h B1h B2h, B0h (max unmap 3FFFC0h, 64 descriptors),

  after TRIM_MODE_OFF the pattern is written): RESULT OK fails=0. The
  system disk (no discard on the image) answers the same, except that
  its blocks keep their data after UNMAP (QEMU ignores the TRIM).
- System shutdown: "Port 0.0: standby for shutdown" (SRB_FUNCTION_SHUTDOWN
  reaches the driver since it declares CachesData).
- File properties of every binary show version 1.5.0.0
  (OriginalFilename ahcint.sys / ahcint9x.mpd).
- trimnt on a 256 MB FAT volume on the AHCI disk (discard=unmap, the
  image with 55 MB of stale blocks): "Scsi2: AHCINT TRIM mode on", the
  free space trimmed, files deleted; the image went from 63.7 MB to
  10.6 MB allocated, sumtool FILES 5 ERRORS 0, CHKDSK clean.
- Release build (bin\ as shipped) on Windows 2000 next to IDENT, MMCSDNT
  and NVMENT data disks: featst RESULT OK fails=0, trimnt, sumtool and

Power management
- Windows 2000 (UP ACPI HAL, QEMU PIIX4 S3/S4 enabled): hibernation
  (S4) through SetSuspendState with NCQ active. The driver is stopped
  through HwAdapterControl, the dump stack loads a second instance
  (Fast Polling, 4.4 KB device extension) which writes the hibernation
  file, and on resume ScsiRestartAdapter sets the HBA up again. After
  resume the four data volumes' CRC32 lists are unchanged, chkdsk is
  clean and a load test passes. The first try failed: the dump stack
  could not allocate the 38 KB device extension of the test build

Shutdown on Windows XP x64 (1.6.0.0)
Looking into a hang at shutdown reported on XP x64 with AHCINT 1.5.0.0
(XP x86 and 2000 not affected on the same machine, as reported). Not
reproduced in QEMU in any of these runs, so the changes in this release
(the one x64-only difference found in the code, and no standby at
shutdown, which 1.4.0.0 did not send either) are not a confirmed fix.
- XP x64 SP1, F6 installation with all four drivers on one floppy
  (system disk on AHCI through AHCINT, an NVMe disk through NVMENT, an
  SD card on a PCI SDHCI through MMCSDNT, PIIX3 disk and CD through
  IDENT), GUI-mode setup at Regional Options, debug builds: shutdown
  from the setup command prompt through NtShutdownSystem (power off) and
  restart: powered off after 5-10 s, restart back at the driver load
  after 15 s. Repeated with 4 CPUs, with 2 GB of the 3 GB RAM above
  4 GB, with a SATA DVD on an AHCI port, with a PCI power management
  capability added to QEMU's AHCI (which has none; Windows did not take
  the HBA to D3 at shutdown), and with a QEMU patch that delays every
  NCQ command after STANDBY IMMEDIATE by 8 s (a disk spinning up): no
  hang. A traced build showed the order on XP x64: the last writes and
  SYNCHRONIZE CACHE / FLUSH, then SRB_FUNCTION_SHUTDOWN (flush, standby),
  and no request after it.
- Windows 2000 SP4, system on AHCI (AHCINT), NVMe data disk (NVMENT),
  PIIX3 disk (IDENT): a file copy and a registry change, then shutdown
  through ExitWindowsEx: powered off, also with the spin-up delay.
- The x64 builds of AHCINT and NVMENT used srb.h's inline register
  accesses (plain volatile, no compiler barrier) where the x86 builds
  call ScsiPort's functions; they now import ScsiPortReadRegisterUlong
  and ScsiPortWriteRegisterUlong as well (MMCSDNT and IDENT already
  did). The release builds of this version ran the XP x64 shutdown runs
  above again (also with RAM above 4 GB): powered off after 5 s.
- NT 4.0 booted from AHCI with the 1.6.0.0 release build: logon screen
  reached, as before.
- Standby at shutdown off by default (as reported, 1.4.0.0 shut XP x64
  down on the same machine; STANDBY IMMEDIATE on SRB_FUNCTION_SHUTDOWN
  was new in 1.5.0.0): XP x64 run above with the debug build, no
  DriverParameters: powered off after 10 s, the log shows no AHCINT
  standby line after the flush. With DriverParameters STANDBY=1: "Port
  0.0: standby for shutdown", powered off after 10 s.
- The new check for registers reading all ones (a powered-off or removed
  controller) was not triggered in any of these runs.
